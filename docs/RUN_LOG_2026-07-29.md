# Real-run findings — 2026-07-29

Notes from executing `paxel-run` against a live project, against `upload.sh`
sha256 `b87487fc7bc420e88ff4baeae4956cb6e2a7b053e44b42f20a3527476733bf74`.

Machine: macOS arm64, Docker 29.5.2, 5.8 GB Docker memory ceiling, 23.5 GB Docker
VM disk. One run, one machine — reported as such.

## The run

```
Auto-detected project: aaquant (1 workspaces)
Git: 382 author-filtered commits (1 email: abhinaykrupa@gmail.com)
Found 4598 sessions + 521 subagents for aaquant (1813MB). Estimated time: ~87 minutes.
```

## THE failure — `ENOSPC`, and none of my original checks caught it

```
Preparing local database...
bin/rails aborted!
Errno::ENOSPC: No space left on device @ dir_s_mkdir - /tmp/paxel-merged-ea089dce
/rails/lib/analyze_local_merge.rb:69:in 'block in AnalyzeLocalMerge.merge_agent_sessions!'
Analysis failed for aaquant (exit code: 1).
```

The merge step writes every session into container `/tmp`. The Docker VM's disk
was **23.4 GB of 23.5 GB used (100%)** while the **host had 204 GB free**. The
container had zero bytes to work with.

This is nastier than it looks because every intuition points the wrong way: `df`
on the host shows plenty of space, memory is fine, the repo is fine. The failure
is in a VM disk most users never look at, and the error surfaces ~4 steps into a
job advertised at ~87 minutes.

Fix: `docker image prune -af --filter until=24h && docker builder prune -af`
reclaimed 5.6 GB (100% → 81% used), and the rerun proceeded.

`paxel-preflight` now checks this by running `df -Pk /tmp` **inside** a throwaway
container and comparing against ~1.5× the transcript volume.

**Suggested upstream fix:** check free space in the container before the merge and
fail fast with the actual number, e.g. *"needs ~1.4 GB in container /tmp, 0 B
available — run `docker image prune`"*. Failing in 2 seconds with a fix beats
failing in 20 minutes with a Ruby backtrace.

## Corrections to my own earlier claims

Running it for real disproved part of what I had inferred from reading the script.
Recording both, because the corrections matter more than the original claims.

### The commit cap is far narrower than I said

I claimed `COMMIT_LIMIT=1000` silently truncated this repo's 1,102 commits. Wrong
on two counts:

1. **The cap applies inside a `--since` window, not to all history.** The run
   reported "382 author-filtered commits" — exactly this repo's **30-day** count
   (`git rev-list --count --since='30 days ago'` = 382), not its 1,102 total. The
   uploader runs `git log -$COMMIT_LIMIT $since_flag`, so the cap bounds commits
   *within the window*. A repo trips it only with >1,000 commits in ~30 days.
2. **The true total is still recorded.** Right above the capped `log`, the script
   runs `git rev-list --count HEAD > ..._commit_count.txt`. So the server receives
   the real count — the numstat *detail* is capped, not the commit *count*. My
   "silent" framing was wrong.

Preflight now evaluates the cap against the `--since` window
(`PAXEL_SINCE` overrides, default 30d) and reports both numbers. On this repo it
correctly says **ok** where it previously cried wolf.

### Scope: one project by default, not all

The uploader auto-detects a single project from cwd; all 221 are scanned only with
`--all`. An intermediate version of preflight scanned globally by default and
over-reported (222 projects / 1.1 GB vs the 4,578 files / 950 MB actually in
scope). Fixed: default = detected project, `--all-projects` models an `--all` run.

Also worth knowing: the uploader's own count (4,598 sessions + 521 subagents,
1,813 MB) **exceeds** the raw `.jsonl` total in the project dir (4,578 / 950 MB),
because it counts subagent transcripts and sidecar data. Preflight measures the
raw dir, so its transcript figure is a **lower bound**, not an exact match.

### What survived

The memory finding stands as measured — 185 MB transcript → 573 MB peak RSS
(3.1×, `/usr/bin/time -l`), and `docker run` still passes no `--memory`. But on
this machine (5.8 GB ceiling) it was **not** the thing that broke the run, and
preflight correctly reported `ok` rather than manufacturing a problem. It would
bite on a 2 GB default ceiling.

## Other observations

- **`Retrying with your default Docker settings` → `Using cached image (pull
  failed, may be offline)`.** The pull failed (almost certainly the same full
  disk) and it fell back to the cached image. Reasonable behavior; the message
  blames the network for what was a disk problem.
- **`Warning: Cursor session extraction had errors. Continuing`** — non-fatal,
  logged to `~/.paxel/logs/cursor-extract.log`. Correct handling.
- **The ~87 minute estimate ignores cache state**, which the tool's own docs call
  the dominant factor ("reruns typically hit 95%+ cache and finish in minutes").
  Minor, but it makes a long run indistinguishable from a wedged one — which is
  what prompted this whole investigation.
